# Puente interno de metadatos v1 — diseño, instalación pendiente y diagnóstico

**Estado (2026-10-17): implementado en código, NO instalado ni verificado bajo identidades Linux.** Este cambio no inicia unidades ni cambia permisos del host. No habilita celdas/VMs ni altera la red. Las pruebas dinámicas de esta iteración siguen pendientes por falta de sandbox OS válido; el resultado anterior de 120/17/4 es histórico, no resultado de este cambio.

## Fronteras efectivas en código

```
sensor (credencial propia, HTTPS al receptor) -> ingestión (escribe events.db privado)
  -> query (UID dystopia-query, SQLite mode=ro/query_only, campos permitidos)
  -> socket Unix /run/dystopia-query/query.sock (SO_PEERCRED exige UID dystopia-control)
  -> control (JWT/rol viewer+, sin ruta ni permisos SQLite de ingestión)
  -> navegador (solo control; sin secreto de servicio) / CSV redactado
```

No hay token administrativo compartido: la credencial de servicio es la identidad Unix del proceso y el propietario del socket. El administrador revoca acceso deteniendo/deshabilitando **socket y servicio query** (la unidad usa `PartOf=` para propagar stop) o migrando la propiedad del socket tras revisión; debe esperar a conexiones en curso y comprobar que no queda descriptor listener. Solo apagar el socket sin detener el servicio no es garantía suficiente de revocación. No hay clave de servicio que rotar; la rotación de identidades Unix requiere un cambio controlado de usuarios/UIDs y unidades. Para hosts distintos **no** usar este transporte ni exponer el socket por TCP: haría falta transporte cifrado y autenticación mutua independiente, pendiente de diseño y autorización.

Cada endpoint de eventos/actividad/CSV en control exige sesión JWT asociada a usuario real y rol viewer+; las API keys genéricas `np_` se rechazan para esta superficie. El lector solo autentica el UID del proceso control y no recibe JWT ni eleva su alcance. El control conserva `InaccessiblePaths=/var/lib/dystopia/ingest`; el lector **no** tiene JWT, cuentas de control, credenciales de sensores, privilegios de administración ni escritura del almacén. El proceso de ingestión sigue siendo el único escritor. El lector tiene grupo primario `dystopia-query`, sin grupos suplementarios; el archivo `events.db` es propiedad de `dystopia-ingest:dystopia-query` y modo `0640`, exactamente. El directorio ingest es `dystopia-ingest:dystopia-query` modo `0710`: el lector puede atravesarlo, **no listar**. `sensors.db` y `server.key` permanecen `0600` propiedad de ingestión y ocultos además con `InaccessiblePaths`. Todos los demás almacenes siguen privados `0600`; `runtime.storage.database()` permite `0640` exclusivamente si `EventStore` recibe el GID de consulta explícito y el propietario es el UID escritor. No aplicar un ACL POSIX que cambie la máscara de permisos inadvertidamente. El lector exige UID escritor, GID lector, modo `0640`, archivo regular único sin enlace, índice recibido y una BD existente: falla con 503 si no se provisionó.

## Contrato versionado y límites

Una conexión socket, una petición JSON en marco de longitud de 4 bytes, respuesta JSON versionada v1. Máximo 4 KiB de petición, 512 KiB de respuesta, 4 consultas concurrentes, timeout de socket 1,5 s, busy SQLite 150 ms, presupuesto de consulta 500 ms con progress handler. `list` acepta 1–100 filas; `export` 1–500, `activity` 5–1440 minutos; periodo por defecto últimas 24 h de **recepción**, como máximo 7 días, sin tiempos futuros mayores de 60 s. No hay SQL, ruta ni selección de BD aportados por el cliente. Los filtros se validan por tipo/enum/IP/identificador y se parametrizan. El índice `received_order` se crea por el escritor en el arranque, **no** por el lector. Es necesario revisar el tiempo de creación del índice en bases preexistentes y la cota de disco antes de reiniciar ingestión.

Las páginas se ordenan `received_epoch DESC, sensor DESC, event_id DESC` y se fijan por máximo `rowid` en un cursor HMAC con clave de proceso efímera y vida de cinco minutos. Inserciones posteriores no aparecen en páginas del mismo cursor; una reinicialización lo invalida (consulta 422, reiniciar filtros). No hay borrado automático de eventos v1: una futura retención cambiará este contrato y requerirá revisión. CSV obtiene conteo y hasta 500 filas en **una sola transacción de lectura SQLite**, con los mismos filtros, orden, instante/cota de recepción y allowlist que la UI. Cabeceras `X-Export-Truncated`, `X-Export-Rows`, `X-Query-At`; no exporta páginas posteriores automáticamente. La ausencia de resultados no prueba presencia de sensor ni seguridad.

Lista explícita de campos que pueden salir de query: `sensor`, `event_id`, `device`, `received_at` (receptor), `observed_at` (sensor, no confiable), `kind`, `source` (IP canónica), `proto` (enum v1). El `payload` completo, estructuras anidadas, credenciales, URLs y comandos **nunca** pasan al control. Los campos no válidos se sustituyen por `<invalid>` o se rechaza el registro; no se intenta redactar secretos del payload por regex. La respuesta del control vuelve a validar la forma, claves y longitudes; CSV aplica protección adicional de fórmulas. Los errores del lector y los rechazos 401/403/422 de FastAPI en rutas de eventos tienen código controlado e ID aleatorio de diagnóstico en `X-Query-Error-ID`, sin rutas, payload ni secretos en logs. Un cursor caducado muestra “Reiniciar paginación”, sin reintento automático. El contador de actividad lee hora de recepción; los relojes declarados por sensores no se usan para periodos o cuotas.

SQLite usa journal `DELETE` en `runtime.storage.EventStore`, no WAL. El lector abre `mode=ro`, `query_only=ON`, `trusted_schema=OFF`, `temp_store=MEMORY`; `BEGIN` establece snapshot coherente de conteo+filas, `COMMIT` lo libera. Una lectura breve puede retener un bloqueo SHARED y demorar brevemente un escritor; el límite de 500 ms y el de concurrencia mitigan, **no prueban** rendimiento con carga real. No usar `immutable=true` en una BD activa. Si en el futuro se cambia a WAL, verificar primero lectura de `-wal`/`-shm` y creación de sidecars bajo identidades separadas: no conceder escritura al lector ni inventar instantáneas incoherentes; hasta entonces no migrar a WAL.

La prueba ASGI/scratch preparada en `tests/integration/test_query_bridge.py` recorre spool de sensor → autenticación de ingestión → SQLite → socket Unix sintético → API de control → CSV y verifica redacción; **no fue ejecutada** por falta de sandbox. Usa el mismo UID con un stub de `SO_PEERCRED`; no demuestra permisos Unix entre identidades distintas. El probe de UID reales y el navegador son ensayos separados.

## Provisión SOLO en Ubuntu 24.04 desechable y autorizado

1. Revisar release, lock/hashes y `runtime.install --dry-run`; aplicar instalador **solo** en el laboratorio con autorización de cuentas/unidades. Instalación nueva crea cuatro identidades (control, ingest, sensor, query) y seis definiciones systemd (cinco services y un socket), pero no habilita ingest/query automáticamente. Instalaciones previas con tres cuentas/cuatro unidades requieren migración explícita: preflight rechaza unidades y permisos antiguos, no sobreescribe ni relaja secretos.
2. Con consola de recuperación, datos sintéticos y servicios parados o ventana acordada, revisar `stat -c '%U:%G %a %n'` de `/var/lib/dystopia/ingest`, `events.db`, `sensors.db`, `server.key`. El directorio de ingestión debe ser `dystopia-ingest:dystopia-query 0710`. Ingestión crea inicialmente `events.db 0600`; el administrador autoriza **solo para ese archivo** `chgrp dystopia-query /var/lib/dystopia/ingest/events.db` y `chmod 0640 /var/lib/dystopia/ingest/events.db`, tras verificar inode/ruta/propietario real y backup. No aplicar a directorio completo, otros DB ni clave TLS. Si se recrea el archivo habrá que repetir provisión; nunca usar chmod recursivo.
3. Antes de iniciar el socket, validar en el laboratorio como usuario query: `test -r` de `events.db`, `test ! -w` de `events.db`, denegación de `sensors.db`, `server.key` y del árbol de control. Como control: denegación de `events.db` y acceso al socket cuando esté habilitado. Revisar grupos efectivos y `systemctl cat` de ambas unidades. Estas pruebas de UID distintos **no se realizaron aquí**. El [probe de permisos](<tests/integration/query_permissions_probe.py>) solo abre descriptores (sin leer contenido/escribir), exige root, marcador `/run/dystopia-query-lab-authorized` root `0600` con contenido `purpose=dystopia-disposable-query-lab`, y `--confirm DISPOSABLE-QUERY-LAB-ONLY`; no usar sobre producción.
4. Tras revisar configuración y `systemd-analyze verify` en Linux (pendiente aquí), habilitar **solo el socket** `dystopia-query.socket`; un GET autenticado desde control lo activa bajo demanda. Confirmar `systemctl status dystopia-query.socket dystopia-query.service`, `journalctl -u dystopia-query.service --since ...` (metadatos/errores, sin payload), `GET /api/console/events` y CSV sintéticos. Desactivar el socket para verificar 503 con ID, no cero. No habilitar el servicio query directamente ni cambiar `InaccessiblePaths` del control.
5. Journald gestiona rotación mediante política del host revisada; este servicio no crea archivo de log ni escribe el payload. Revisar retención/cotas de journald y backup seguro separado; no copiar DB, WAL o logs a consola ni a informes.

## Diagnóstico sin secretos

- 401/403: revisar JWT, usuario/rol en control; no pasar JWT al lector. `DENIED` en socket: verificar propietario/mode del socket y UID de proceso con `systemctl show`/`stat`, no imprimir credenciales.
- 422: periodo superior a 7 días, filtro inválido, cursor caducado/alterado o exportación fuera de límites; limpiar filtros/cursor y volver a consultar. No reintentar consultas inválidas automáticamente.
- 503 con `X-Query-Error-ID`: socket deshabilitado, identidad incorrecta, DB/índice ausente, permisos, bloqueo, presupuesto o servicio caído. Correlacionar el ID con la advertencia del control `event_query_failure`; el lector no registra rutas ni datos de eventos. Si el socket no está configurado, control genera un ID local.
- 200 con lista vacía: consulta válida sin registros en el periodo; comprobar ingestión **por canal local autorizado**, nunca inferir conexión de sensor.
- Reinicio del lector revoca sus cursores HMAC; reiniciar la paginación sin reenviar mutaciones.

## Credenciales temporales previamente expuestas

En la demostración anterior se creó una contraseña sintética y un secreto JWT de loopback en archivos temporales bajo `/tmp/dystopia-ui-*`. El proceso se detuvo y esos archivos/estado se eliminaron en la iteración previa. El 2026-10-17 se confirmó **sin leer valores** la ausencia de `/tmp/dystopia-ui-password`, `/tmp/dystopia-ui-current`, `/tmp/dystopia-ui-d9WP` y de procesos `runtime.cli control|ingest|query`. El JWT anterior solo sería aceptado por un servidor que reutilizara **el mismo secreto y hash/rol de usuario almacenado**, durante su vida (normalmente 30 minutos); borrar un archivo de contraseña **por sí solo no revoca** tokens ya firmados en un proceso vivo. La eliminación del estado de usuarios y el proceso detenido invalidan el acceso a esa instancia, pero no se auditó ningún host o backup ajeno. Las pruebas preparadas comprueban que cambio de contraseña o borrado de usuario invalidan tokens por `ver`/usuario, pendientes de ejecutar en sandbox.

Si un responsable descubre reutilización del secreto demo fuera de esa instancia: localizar copias y servicios **sin imprimir el secreto**; detener acceso, rotar únicamente la clave JWT afectada según procedimiento administrativo autorizado, invalidar sesiones, revisar auditoría y verificar que no se restauró el mismo hash/rol desde backup. No rotar secretos globales sin evidencia y autorización. No reescribir Git ni borrar evidencias.
